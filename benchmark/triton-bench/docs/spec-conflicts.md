# 技术报告条文冲突清单（MVP 实施回报）

本报告记录 MVP 实施过程中发现的、技术报告（`docs/Triton编译器评测体系技术报告.md`）
内部或与实测环境冲突之处，以及本项目采用的口径。

每条目给出：**冲突原文 → 冲突原因 → 本项目采用的口径 → 建议修订方向**。

## C1 · 跨赛道总分：§3.3 与 §6.4 直接矛盾

- **§3.3 第 3 条**：「Coverage 分数高不代表性能好，反之亦然；两赛道分数不做隐式换算」
- **§6.4**：`Total = 0.40 × Coverage + 0.45 × Performance + 0.15 × Stability`

`Total` 就是把两条赛道换算成一个数，与 §3.3 的禁止条款直接冲突。
且 0.40 / 0.45 / 0.15 这组权重在报告中没有推导依据。

- **采用口径**：**不产出 `Total`**。两条赛道分数分列披露，各自解释。
- **建议修订**：删除 §6.4 的 `Total` 合成，改为「两赛道分别排序，不做加权合成」；
  若确需单一排序，需单列一章论证权重来源。

## C2 · 容差：§6.1.1 单组数值不适用

- **§6.1.1**：`tolerance: {rel: 2.0e-2, abs: 1.0e-4}`

该组数值对 `float32` 过松（`rel=2e-2` 会放过静默错误），对整型完全不适用
（整型只能要求精确相等）。

- **采用口径（tolerance.yaml 1.1，2026-10-11 标定）**：按 dtype 分级。
  整型 `rel=abs=0`；`float32` rel 1e-4 / abs 1e-5；`float16` rel 1e-3 /
  abs 2e-3；`bfloat16` **rel 7.8e-3**（=2⁻⁷，容纳 1 ULP——bf16 的 1-ULP
  相对误差理论区间是 (2⁻⁸, 2⁻⁷]，旧值 5e-3 落在区间内会冤枉 binade 下
  半段的合法舍入；实测 swi_glu-bf16-M40 参考量级 ~336 处 1 ULP=2.0
  即 rel 5.95e-3 被错杀）/ abs 1e-2。参考精度统一 `float32`（昇腾不支持
  fp64，见 C9）。**禁止 case 级覆盖**（schema 层面 `extra="forbid"` 强制）。
- **算子级覆盖（新增机制）**：仅当参考实现（torch 在昇腾上的输出）**自身**
  偏差超过 dtype 默认档时，在 `operator_overrides` 登记该算子该 dtype
  的覆盖档，**每条必须附归因证据**（实测复现）。已登记两条（均修
  ADV-C1 静默错误冤案）：
  1. `gelu.float32` abs 1e-5 → 1e-3：昇腾 NPU 的 f32 gelu 以默认模式
     （approximate='none'，语义要求 erf 精确式）调用时实际返回 tanh 近似
     精度的结果——与 erf 精确式差至 4.73e-4，且与 |tanh−erf| 在各用例
     输入上的最大差逐位吻合（S120: 4.589e-4；M48: 4.732e-4 ≈ 实测
     4.735e-4）；tanh 模式用例双方同为 tanh 不受影响。放宽后两种合法
     写法都过，真错（误差 ~1e-1）仍拦。
  2. `grouped_matmul.float32` abs 1e-5 → 1e-3：extreme 输入（|x| 至 ~84）
     × K=128 的 f32 累加，参考自身与 f64 真值差 max_abs 6.0e-4 /
     max_rel 1.6e-3（本地复现）——默认档比参考自身噪声还紧两个数量级。
  3. **B 类覆盖（跨实现求和顺序噪声，2026-10-13 登记，tolerance 1.2）**：
     与上两条（参考自身偏差，A 类）不同类：任何合法实现与 torch 的
     **求和顺序**不同，长 K / 大规模归约下顺序噪声超过默认档。归因探针
     （probes/dot_precision.py，记录 6844…-manual-1013-234810）实测
     f32 分块 tl.dot 与 torch matmul 在 K≤1024 **逐位一致**、K=2048
     分歧 max_abs 1.8e-4、K=65536 分歧 max_abs 4.7e-3，且 BK=32/128
     逐位相同——噪声与分块无关，实现侧无抓手。据此登记四条：
     `transpose_linear.float32` abs 1e-3（[2048,2048] 实测 2.6e-4）、
     `rms_norm_linear.float32` abs 1e-2（[64,65536] 实测 5.9e-3）、
     `grouped_matmul_swiglu.float32` abs 5e-2（两段 GEMM 经 silu·b
     级联放大，实测 2.4e-2）、`unsorted_segment_sum.float32` abs 1e-3
     （~4096 元素段归约，实测 2.7e-4，本地按内核求和序模拟 2.4e-4
     同量级）。登记前三个 f32 大 K 用例连续三轮如实判错；登记后按
     证据口径通过，10× 于噪声量级的真错仍拦（重放钉
     test_fusion_f32_order_noise_overrides_replay_real_machine）。
- **建议修订**：§6.1.1 改为「容差按 dtype 查表，见 tolerance.yaml」，删除单组数值。

## C3 · 双 oracle：TRITON_INTERPRET 在被测编译器上不可用

- **§4.2**：双 oracle（PyTorch eager + NumPy float64 + `TRITON_INTERPRET` 交叉）

实测结论：`triton-ascend` 3.2.1 的 `triton.knobs` 模块损坏——
`ImportError: cannot import name 'getenv' from 'triton._C.libtriton'`。
**在干净 venv 中全新安装后仍然如此**，说明这是被测编译器自身的能力缺失，不是环境污染。
因此 `TRITON_INTERPRET` 环境变量根本无法被读取，解释器不可用。

另有方法论问题：`TRITON_INTERPRET` 是 triton 的一部分，而 `triton-ascend` 是 triton 的 fork。
用它验证 triton-ascend 存在循环论证。

- **采用口径**：**单 oracle 判定**（torch eager on NPU）+ **第二参考实现交叉校验**
  （corpus 内每个算子附一份 CPU 路径参考实现，与主 oracle 比对；不一致 → `ORACLE_FAIL`）。
  不为双 oracle 设计仲裁逻辑。
- **建议修订**：§4.2 增加「被测编译器不支持 interpreter 模式时的降级方案」；
  并说明 `TRITON_INTERPRET` 只能作为弱信号，不能作判定依据。

## C4 · 性能归一化锚点：B0 在昇腾上不存在

- **§3.4.6 / §6.3**：`P_ref_geo` 取「同硬件上官方 Triton 上游对应版本」的几何平均加速比

上游 Triton 只支持 NVIDIA / AMD，昇腾平台上**不存在可安装的上游 Triton 实现**，
`triton-ascend` 就是昇腾上的 Triton 全部。因此 B0 不可得，§6.3 的 0–100 归一化算不出来。

- **采用口径（2026-10-11 修订：轮级首轮锚点 → 按算子锚点）**：
  锚点**按算子**冻结——某算子题库内全部用例都判对的最早一轮，该轮该
  算子加速比的几何平均冻结为该算子的 100 分尺子；每轮逐算子出分，轮级
  性能分 = 有分算子的加权平均。轮级「首轮基线」口径因死锁缺陷废除
  （论证见 C10）。`baseline_anchor_ref` 固定为 `PER-OP`，报告中固定声明：
  「相对本评测体系各算子首次全对轮次」的口径，**不是跨编译器对照**。
- **建议修订**：§6.3 增加「无参考编译器时的锚点定义」小节。

## C5 · corpus 规模：MVP 与规划指标的关系

- **§3.4.4 / §7.4**：≥1000 case，FA 覆盖 ≥90%（建议 ≥95%）

MVP 的目标是「打通流程」，1000 case 背后拖着整个生成层（抽取器、libcst 变异、
覆盖引导引擎、MinHash 去重、四道门禁），与链路是否成立无关。

- **采用口径**：MVP 冻结 **20 个 case / 5 个算子**；**schema 字段不缩**
  （`seed` / `feature_atoms` / `launch` / `content_hash` 全保留），
  使 P1 灌数据时只改内容不改代码。
- **建议修订**：明确分期——MVP 验证链路，P1 扩规模并达标。

## C6 · capability manifest / UNSUPPORTED：MVP 不引入

- **§4.9**：被测方提交 capability manifest 声明不支持的特性，据此剔除 case 为 `UNSUPPORTED`

该机制可被用于「声明不支持全部难题」来刷分，是防作弊的反面。
且 MVP 没有第二个编译器提交者，机制无服务对象。

- **采用口径**：**不引入 `UNSUPPORTED`**。全部 case 计入分母，FAIL 就是 FAIL。
- **建议修订**：§4.9 增加滥用防护（如剔除比例上限、争议仲裁）。

## C7 · 算子权重：MVP 取等权

- **§3.4.4**：权重由 profiler 采集「调用频次 × 耗时占比」标定

该标定属 P1 工程。手工拍权重会污染 `OpScore` 的解释性。

- **采用口径**：MVP 全部算子权重 = 1.0（等权），诚实、可解释、无争议。
- **建议修订**：明确权重标定为 P1 交付项，MVP 等权。

## C8 · 存储选型：MVP 用 SQLite

- **§5.1**：PostgreSQL（元数据 / 榜单）

MVP 单执行点、无并发写入，PG 的运维成本无收益。

- **采用口径**：SQLite 单文件。schema 不使用 SQLite 专有类型，迁 PG 只需改连接串。

## C9 · 参考精度：昇腾不支持 float64，不能用作高精度锚点

- **§4.2** 提到用「NumPy float64（标定）」作高精度参考

实测：`torch.zeros(4, dtype=torch.float64, device="npu:0")` 不报错，
但运行时打印：

```
Warning: Device do not support double dtype now, dtype cast replace with float
```

即 **float64 被静默降级为 float32**。若把参考实现精度设为 float64，
得到的是一个假的锚点——你以为在比 float64，实际全是 float32。

- **采用口径**：`reference_dtype: float32`。
  误差的**计算过程**放在 CPU 上以 float64 进行（CPU 支持 fp64），
  这样误差值本身是精确的；但两个参考实现的**运算**都用 float32，
  避免交叉校验把「精度差异」误判成「实现差异」。
- **建议修订**：§4.2 删除 float64 标定，改为注明「昇腾平台无 fp64，
  参考精度取 fp32；误差计算在 CPU 侧以 fp64 进行」。

## C10 · 首轮锚点：需质量门槛，且对数口径在锚点接近 1 时失真

- **§6.3**：`Performance = 100 × ln(P_geo) / ln(P_ref_geo)`

实测暴露两个缺陷：

1. **锚点无质量门槛**。首轮若含 `ORACLE_FAIL` / `WRONG_RESULT`（run 3 就是，
   3 个 ORACLE_FAIL + 2 个 WRONG_RESULT），它仍会被冻结为锚点，
   等于把一次被污染的运行固化成标准。后续因此算出 120.69 分——
   超过 100，口径已失真。
2. **对数公式对锚点接近 1 的情形数值不稳定**。实测：
   `P_ref=1.05` 时 `P_geo=1.5` 算出 **831 分**；`P_geo<1` 还会出**负分**。

- **采用口径（2026-10-11 修订：轮级「全有或全无」门槛 → 按算子资格）**：

  修订论证（与任务方讨论定案）：轮级「全部计入用例都 PASS 才有资格当
  基线」的门槛有**死锁缺陷**——题库混进一道坏题（无论谁交都过不了），
  任何一轮都不干净，锚点永远冻结不了，性能赛道整体死锁。轮级门槛把
  「尺子是否存在」耦合到「有人交出全对实现」上，现实（240 题含超大
  负载）中可能永不发生。

  - 锚点资格**按算子**判定：某算子全部题库用例都 PASS 且都有加速比的
    最早轮次 = 该算子的锚点。「全对」隐含两道门槛：判错用例的加速比
    不进性能统计（「错得快」此前会给 P_geo 充值，真缺陷）；参考失效
    的用例不可能是 PASS（run-3 那类考场侧污染自动出局）。
    `--limit` 跑一半 / 冒烟档（无性能数据）天然不满足资格。
  - 死锁半径缩小到单算子：坏题只废它所在的算子（该算子永远出不了
    性能分、被大声暴露），其余算子照常出分。
  - 数值护栏保留：锚点偏离 1 不足 0.10 → 该算子口径**不可用**；
    得分落在 `[0, 500]` 之外同样不可用；
    **「无法计算」必须是空值，不能补 0**——补 0 会把「算不出来」
    伪装成「性能极差」。
  - 锚点跨题库版本不通用（题不一样，尺子不能借）。
  - **亚线性锚点（<1）的方向反转修复（scorer 0.2.2，2026-10-12）**：
    首次真机测速冻结的锚点是 0.14x（demo transpose 内核比官方框架慢
    约 7 倍）——旧公式 `100·ln(P)/ln(锚点)` 在锚点 <1 时两个对数均为
    负，方向反转：内核优化快 2 倍（0.14→0.28x）算出 64 分、慢 2 倍
    算出 135 分，快慢颠倒。改为统一公式
    `100 + 100·ln(P/锚点)/|ln(锚点)|`：锚点>1 时与旧公式**代数恒等**
    （全部既有行为不变，回归测试不改即过），锚点<1 时方向正确
    （快 2 倍 ≈135 分、慢 2 倍 ≈65 分、追平框架 1.0x = 200 分）。
    该情形不是边角：真机上 triton 内核对多数算子尚未跑赢 ATen，
    首个锚点大概率是亚线性的。
- **建议修订**：§6.3 增加锚点质量门槛与归一化公式的适用边界。

## C11 · `num_warps` / `num_stages` 在昇腾上不生效

- **§6.1.1**：`launch.block_config: {BLOCK_M, BLOCK_N, num_warps, num_stages}`
- **§7.1**：D5 优化 pattern 维度含 `num_warps`、`num_stages`

实测：triton-ascend 3.2.0 在收到这两个参数时打印

```
[WARNING] Please DO NOT tune args ['num_warps', 'num_stages']!
```

原因：二者是 **NVIDIA GPU 特有概念**（warp=32 线程束、stages=软件流水级数），
昇腾 AI Core 架构不同，不接受这两个编译参数。（3.2.1 静默忽略，3.2.0 会警告。）

两点影响：

1. **日志污染**：每个 case 都打一行，规模化后不可用。
2. **规范层面的空洞**：报告把这两个列为「固定 config」和优化 pattern 的维度，
   但在昇腾上它们本就不生效——那么「禁 autotune、固定 config」这条性能主口径，
   在昇腾上实际能固定的只有 **BLOCK 与 grid**。

- **采用口径**：kernel 改为「**配置里显式给出才传**」（`_launch_kwargs`）。
  昇腾环境的 case 配置不写这两个字段，不触发警告；NVIDIA 环境写上就照常生效。
  同一份 kernel 保持硬件无关。
- **建议修订**：§6.1.1 与 §7.1 注明 `num_warps` / `num_stages` 为 NVIDIA 特有，
  昇腾上不适用；昇腾的固定 config 维度应重新定义。

## C12 · manifest_hash 必须只覆盖内容，不能包含 frozen_at

实测：同一份 corpus 连续生成两次，得到完全不同的哈希

```
第 1 次：f2cf68f9080859197f96d417489c2c0a1fd3ec05bc6019b37243b9b69a7f43d1
第 2 次：43e0b89424d12cd730a3c262340e98a05c22ccc7717a57abb77933f722ec5653
```

根因：`frozen_at`（时间戳）参与了哈希计算。

后果（三条都不轻）：

1. **无法判断两次运行是否用了同一份 corpus** —— 内容相同却哈希不同，
   而「跨运行可比」的前提正是 corpus 相同
2. **「冻结」语义失效** —— 本该标识内容的指纹却在随时间变化
3. **污染版本控制** —— 每次 `build_corpus.py` 都让 manifest.json 产生 diff，
   被迫在 `git pull` 前手工 `checkout` 该文件

- **采用口径**：`manifest_digest` 排除 `frozen_at` 与 `manifest_hash` 自身，
  只覆盖 `version` / `spec_version` / `feature_atoms_version` /
  `operators` / `cases` / `excluded`。
  修后连续两次生成均为 `681d3223...`。
- **建议修订**：规范中明确「corpus 指纹 = 内容指纹」，时间元信息不参与。

## C13 · 融合算子是否强制单内核：不强制（2026-10-13）

**冲突**：算子组合维度的融合算子（LinearGelu / RmsNormLinear / MoeGating
等），"融合"的本意是多个语义段在一个内核里一次完成。是否要求提交方
用**单个** triton 内核实现（内核内完成两段），还是允许**多个内核串联**
（每段一个内核、host 侧依次调用）？

**决策：不强制单内核。** 判定口径：

- **正确性**：无论单内核还是多内核串联，结果判定完全一致（同一容差体系）；
- **反作弊**：既有规则不变——任何一段的核心计算都不得委托框架内置
  函数、不得主机往返、不得自动调优；分段串联时每段都必须是提交方自己
  的 triton 内核（串联 torch 内置算子仍判 SUB-STR-001）；
- **性能**：**性能差距正是该维度的测量对象**——两内核串联比单内核
  融合多付一次中间结果读写与一次启动开销，这个差距体现在加速比与
  按算子性能分上，而不是判定作弊。用评分区分实现质量，不用规则。

**为什么不用规则强制**：验证"是否真的单内核"需要分析编译产物或内核
计数，静态扫描不可靠（包装层可以隐藏多内核调用），产物级分析对跨
平台的 triton-ascend 缺乏稳定接缝——为一条无法可靠执行的规则引入
误判面，不如让测量本身说话：融合做得差的实现，加速比自然低。

**影响范围**：示范提交（examples/demo-submission）的 11 个融合内核
按此口径实现——TransposeLinear 用"步长互换"在单内核内完成转置段
（教学上展示融合写法），RmsNormLinear 拆成归一化系数 + 融合收缩两
个内核（scale 是逐行标量，不算中间结果落盘）——两种写法都合法。

## 附一 · 编译链确证（回答「是否真的编译成昇腾产物」）

之前的验证只证明了「结果正确」，未证明「真编译」——理论上存在
triton-ascend 对简单算子走 ATen 等价替换而非真编译的可能，
那样测的就是 ATen 而非编译器。已在昇腾 910B4 上实测确证：

| 证据 | 实测值 |
|---|---|
| 冷编译 + 执行 | **22604.66 ms** |
| 热执行 | 0.275 ms |
| 冷/热比 | **82230 倍** |
| 编译缓存 | `~/.triton/cache/`，9 个产物，共 69 MB |

产物链条（与报告 §1.2 描述的编译链一致）：

```
add_kernel.ttir        Triton IR（前端）
add_kernel.ttadapter   昇腾适配器（triton-ascend 特有）
add_kernel.npubin      ★ 昇腾原生可执行二进制
npu_utils.so           NPU 运行时辅助
launcher_*.so          launcher
precompiled.h          华为版权头 Copyright (c) Huawei Technologies
```

`.npubin`（NPU binary）是关键——确证产物是昇腾原生机器码，
而非 ATen 回退或 CPU 解释执行。

**附带结论**：JIT 缓存在昇腾上生效（热执行 0.275 ms），
报告 §6.5「冷编译单独计时（清空缓存路径）」这条规则可落地，
但需注意**冷编译在昇腾上耗时可达 22 秒**，远长于 NVIDIA，
规模化执行时必须依赖缓存复用或预热，否则 1000 case 将不可行。

## 附：实测发现的两条工程约束（建议写入规范）

1. **`@triton.jit` 依赖源文件**：`inspect.getsourcelines` 反查源码，
   从 stdin / `exec` / `eval` 加载的 kernel 一律失败。
   → corpus 必须是文件系统上的真实目录，kernel 不能存进数据库再执行。

2. **`triton` 与 `triton-ascend` 安装目录同名**：安装社区 `triton` 会覆盖并静默破坏
   被测编译器（实测：pip 元数据 3.5.0 而 `import triton` 为 3.2.0）。
   → 评测工具链依赖清单禁止出现 `triton`（已由 `tests/test_deps_guard.py` 机器校验）；
   → 每次运行前必须跑健康探针，失败则整轮判 `INVALID`。

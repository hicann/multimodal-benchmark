## 三、七道强制关口

### 关口 1：冻结输入，保证不漏项

读取所有工作表和每个非空行；保留全部原始列以及非未解决状态行，不自动去重。同内容重复行仍各自拥有基于“输入哈希、工作表、实际行号”的 `issue_id`。

每次显式给出预期未解决总数。缺必填列、未知状态、非法路径、重复表名、损坏数据、未知工作表结构、缺任务、重复任务都报错，不把输入异常解释为零问题。空报告也不能直接证明清零。

冻结回执记录 XLSX、全部原始行、目标提交、完整源文件与模式快照、控制器版本。状态目录置于目标仓库之外，不污染待评测源码。

### 关口 2：一条问题一份任务，跨文件问题不得只修主文件

149 个任务恰好覆盖 149 条原始问题。重复代码从 `file path` 提取全部成员；重复文件从描述列提取全部成员。成员路径逃逸、缺文件或非普通文件不能被当作已修复。

任务内置对应规则的待核验计划，规则分派位于 `scripts/codecheck_policy.py`。每类都写明：需核实的根因、允许的修复方向、安全限制和必需回归。该计划只是工作义务，**不是已分析或已修复证据**。

队列默认所有者为 Codex。优先处理本轮新描述/新位置，再处理未完成的既有条目；暂缓项独立列出但不从总数消失。跨任务改动相关文件时，必须重审所有受影响任务。

### 关口 3：先解释根因，再提交修复

每项决策必须提交六个非空字段：

1. `root_cause`：为什么触发，涉及哪个真实对象/分支。
2. `plan`：具体调整和全部影响范围。
3. `acceptance`：该条如何被判断为消除，有什么未知边界。
4. `regression_tests`：对应测试名称和为什么能覆盖变化。
5. `safety_constraints`：签名、ZIP 自足性、评分、反作弊、参考身份等约束。
6. `reason_if_not_fixed`：未修原因；若已改写明“不适用”和仍待验证内容，不能留空掩盖。

状态只允许 `ANALYZED`、`PATCHED`、`LOCAL_VERIFIED`、`BLOCKED`、既有 `DEFERRED`。不接受 `DONE` 或手工 `REMOTE_CLOSED`。模糊说明的质量仍需上下文审阅，非空校验不能证明文字正确。

复杂重构须由 Codex 阅读上下文；只有可证明不改变语义的修改才交给机械脚本。不得修改签名、分母、容差、拒绝条件，删除负向测试，或通过别名、动态拼字、排除配置逃避质量扫描。

### 关口 4：执行验证，不接受自报测试通过

由控制器执行命令，记录工作目录、参数、可执行文件哈希、版本探测、退出码、超时、标准输出/错误、测试结果和源码指纹。真实命令失败也保存证据，不转换成成功。

pytest 回归由控制器产生 JUnit，记录失败/错误/跳过；空测试、全部跳过、非零退出均不能算通过。只给 `echo PASS` 或普通命令退出成功，最多得到 runner 成功，不能产生语义验收。

当前自动适配器明确限定范围：

- 方法顺序：验证本条显式 AST 关系；只能是 `LOCAL_PROXY_CLEAR`，不是整个门禁规则通过。
- 重复文件：成员字节相同可证明仍有重复；成员不相同仍可能有逻辑重复，保持 `UNKNOWN`。
- 缺成员或未知规则：`UNKNOWN`，不得默认为通过。

当前执行层仅允许“显式顺序代理清除 + 实际定向回归”登记 `LOCAL_VERIFIED`。其他规则需要补充经审阅的专用适配器，不能借通用 lint 日志登记已验证。即使 `LOCAL_VERIFIED` 也继续等待远程验收。

全量回归应与**同基线**失败清单比较；现有两项基线失败必须保留、具体解释，不能把带失败的运行说成全通过。当前执行器对非零回归严格报失败；未实现自动基线差分豁免，不冒充已拥有该能力。

### 关口 5：防止旧证据被后续修改复用

每条决策引用执行事件序号；事件串接前序哈希，并独立保存尾部回执。源码、文件模式、关联文件、控制器改变后，旧结论显示 `STALE`，不能继续使用。证据日志缺失/变更、事件缺页或尾部删除均使验收失败。

同一轮多项修改可以共享同一最终快照上的完整回归，避免每个 issue 重跑全量；但早期单项测试不能自动证明最后一次合并后的字节正确。最终必须重跑定向与全量，并重新绑定所有受影响项。

本地哈希/事件链不是对拥有全部写权限的恶意修复器的密码学防篡改：如果同时篡改控制器、输入和回执，仍须用户/CI 独立保管原始导出、扫描元数据与审批记录。

### 关口 6：整类规则回查与复扫对账

不是“原行号没了就结束”，而是同时检查：

- 原始 149 个任务是否逐条仍有结果。
- 同类规则在整个相关模块/类是否重新产生新位置、新对象。
- 本轮补丁是否引入新问题，例如新 helper 超长、重复片段迁移、局部导入遮蔽。
- 新报告是否覆盖同一提交、相同有效配置和完整范围。

后续 XLSX 必须建立新基线，保留旧基线和事件。`reconciliation.json` 同时给出原描述匹配、歧义、未再列出、新描述及同类复报。缺服务端 defectId 时只做候选匹配，多个相同描述不能任意配对。

当前工具**没有**在缺服务端元数据时自动判定远程关闭的功能；`complete` 保持 `false`。要最终验收，需要服务端扫描提交/配置/范围、对应复扫详情及逐项映射。负责人确认的例外必须单列，不计为已修复。由用户确认这些材料后再实现经审阅的远程验收适配器，不让 Codex 自填“已关闭”。

### 关口 7：统一交付与评测功能回归

实际重构在可写候选副本完成，最终一次应用到目标仓库。应用器检查完整基线漂移、备份、原子替换、异常回滚和幂等；应用后核对交付指纹等于已测快照。

重复文件物化必须保证最终 ZIP 自足；认证资产变更采用显式修订、保留旧索引与历史，不改评分和参考语义。最终真机验收复用 `scripts/submission-simulation-verify.sh independent` 和 `normal`，分别验证新合法实现、合法边界、负向拒绝及“ZIP 上传→解析→运行→评分→结果查询”。真机证据缺失时必须保留 `NOT_RUN`，不能把本机 pytest 当作 NPU 证明。

## 四、Codex 的实际工作节奏

1. 每次开始先运行 `verify`、`gate`，读取优先队列和所有 `TODO/STALE/BLOCKED`；不得凭聊天摘要选几项就忽略余下项。
2. 按任务读取所有成员与引用方，完成具体分析，再修改并回归。每项记录决策和证据；跨文件可以合并实施，但不能合并掉原 issue 身份。
3. 一批修改后执行整类规则回查、新增告警检查及基线差分；失败则继续修复，不将本地代理规则调宽以满足数字。
4. 最终统一冻结候选、回归、生成应用器；没有完成项的明确去向时不能声称完整交付。
5. 每轮向用户报告固定口径：原始总数、暂缓、待处理、分析中、已改待验证、本地已验证、阻塞、过期、远程确认关闭、新增告警。所有状态互斥相加应等于该基线任务数；新增单列但必须进入后续总队列。

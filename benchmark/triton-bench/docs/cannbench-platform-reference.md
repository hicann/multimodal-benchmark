# CANNBench 评测平台前端参考（供 Triton-Ascend 评测平台设计借鉴）

> 采集时间：2026-11-11，站点 `https://cannbench.com/`，真实浏览器逐页试用。
> 两轮采集：第一轮为访客（未登录）视角；第二轮通过 GitCode 账号登录后补全提交表单、个人工作台、账户与方案管理等登录态页面。
> 落点：本文件对应 `docs/评测体系要求.md` 中「面向持续运行的评测平台与工程资产建设」一项，作为平台原型的功能与交互参考。
> 证据分级：**[实测]** = 浏览器中直接操作/观察到；**[实测·登录]** = 登录后可见；**[文档]** = 站内 `/docs` 公开说明；**[缓存]** = 浏览器 `localStorage` 中可见的前端数据契约。文末附录列出未覆盖区域。
> **重要**：站内文档与当前线上 UI 存在多处口径差异（ZIP 体积、额度、Token 有效期、方案管理权等），已统一汇总到 3.6 节「实测校正」，设计时以 UI 实测值为准。

## 1. 平台定位与整体形态

CANNBench 是「提交算子实现 → 在真实 Ascend NPU runner 上评测 → 汇入公开榜单」的在线平台，站内自称 **BenchSite** 控制平面。其开源仓库 `gitcode.com/cann/cann-bench` 只覆盖评测体系（任务规格、评测器、评分公式、贡献流程），**网站前后端未开源**；本文是对线上界面的黑盒观察。

### 1.1 站点地图 `[实测]`

| 路由 | 页面 | 访客可见性 |
|---|---|---|
| `/` | 概览 | 公开 |
| `/benchmarks` | 评测集列表 | 公开 |
| `/benchmarks/{slug}` | 评测集详情（概览 / 接口两个页签） | 公开 |
| `/leaderboard` | 排行榜 | 公开，功能最完整 |
| `/submit` | 提交算子 | 登录墙 |
| `/docs` | 接入文档（多页签 + 配置生成器） | 公开 |
| `/updates` | 平台动态 / 版本发布 | 公开 |
| `/workspace/jobs` | 个人工作台 | 登录墙 |
| `/workspace/jobs/{job_id}` | 任务详情与日志 | 登录墙 |

顶部导航为「概览 / 评测集 / 排行榜 / 提交 / 文档 / 动态」六项，当前项带下划线高亮；登录后 header 额外出现「工作台」。右侧为「主题」下拉与「登录」按钮。页脚分「CANN 资源」（开源组织、仓库、技术报告 PDF、示例代码、昇腾社区）与「站点」两组链接；右下角有全局悬浮的「问题讨论」胶囊按钮，指向 GitCode discussions。

### 1.2 全局交互与视觉 `[实测]`

- **主题下拉**：`日间 / 夜间 / 跟随系统` 三个单选菜单项（`menuitemradio`），默认日间。
- **登录**：点击后跳转 `gitcode.com` OAuth 授权页（`client_name=cannbench`、`scope=all_user`、`redirect_uri=/api/auth/gitcode/callback`，`state` 内含 `return_to` 与 `nonce`），授权后回跳原页面。
- **视觉语言**：浅色底 + 白色卡片 + 细边框；Hero 区用紫蓝渐变波浪背景、渐变强调字与手绘下划线；按钮为胶囊形；指标数字用大字号 + 语义色（绿/橙/红）；`BETA`、`NEW` 用小型徽标；KPI 卡为「图标 + 指标名 + 大数字 + 辅助说明行」四段式。
- **指标口径提示**：`基础加速比`、`理论加速比`、`中位基础加速比` 等名称旁带 `!` 图标，hover/focus 显示解释（如「相比 Agent 生成的未经优化的算子性能的加速比」）。列名与 KPI 名都带解释，避免用户误读指标。

### 1.3 关键规模快照 `[实测]`

首页全局 KPI：`60 算子` / `最高分 8591.8` / `52471 提交` / `1256 用户`。
排行榜（official-tasks 2.0 · 950DT 口径）：`44 个方案`、最高总分 `4495.33`、中位基础加速比 `0.752×`（理论 `0.06×`）、通过率 `40.8%`（`21517/52800 测例`）。
> 注意：首页「最高分」与榜单「最高总分」数值不同，说明**全局概览与筛选态榜单采用不同统计口径**——这是设计上容易踩坑的一点，平台应显式标注每个 KPI 的筛选范围。

## 2. 逐页功能与交互细节

### 2.1 概览 `/` `[实测]`

- Hero：一句价值主张 + 三个 CTA（浏览算子 / 查看排行榜 / 提交算子）。
- 「公开评测基准」三栏资源卡：GitCode CANN 社区、CANNBench 开源仓、评测体系设计。
- 全局统计条（4 个数字）。
- 「Why CANNBench」四张价值卡：真实硬件结果、统一任务口径、失败也能定位、看得懂的比较。
- 评测集卡片：`official-tasks v2.0.0`（5 等级 / 60 算子 / 1200 用例）、`Micro-official-Tasks v2.0.0`（5 等级 / 16 算子 / 320 用例），卡内直接给「提交算子」入口。
- 「怎么开始评测」四步引导：从任务规格开始（下载模板）→ 提交算子实现（选择评测集）→ 在 Ascend NPU 上运行（查看任务）→ 在排行榜上比较（查看榜单）。
- **Runner 状态卡**：`NPU runner 就绪`、终端风格 `$ cann-bench await`、`阶段 · 空闲`、「当前无运行任务，提交算子后可在此实时查看评测过程」；旁边是「动态 · 最新」实时提交流。把**基础设施在线状态**和**提交活动流**放在首页，是很值得借鉴的运营化设计。

### 2.2 评测集 `/benchmarks` 与详情 `[实测]`

列表页按评测集分块，每块头部含：名称、变更说明、版本 + `BETA` 徽标、等级数 / 算子数 / 用例数，右侧「提交算子」「下载参考包」。

下方按难度等级 `L1 基础级 ~ L5 宗师级` 组织卡片，每卡含：等级描述、算子名标签（超出部分折叠为 `+8`）、算子数 / 用例数。算子名可点进规格文档。

详情页 `/benchmarks/official-tasks`：
- 面包屑 `评测集 / official-tasks`，`BUNDLE 2.0.0 BETA` 版本标，变更说明。
- 「最佳提交」区（`共 N`，空态时「暂无提交 / 成为第一个提交者」）+ 下载参考包（`/api/benchmarks/{slug}/reference`）。
- 三个页签按钮：`排行榜 · N` / `概览` / `接口`。
- **「接口」页签是平台最有价值的信息架构**：左侧 `API 说明 · 60 DOCS` 算子列表，每项显示 `算子名` + `L1 · 20 CASES`；右侧渲染该算子的 `desc.md`，提供「复制 Markdown」。文档章节固定为：1. 算子简介（含难度等级、特征、场景）、2/3. 接口与测例说明、4. 精度判定标准（`MERE`/`MARE` 公式 + 各 dtype 阈值表 + 通过条件）、5. 标准 Golden 代码、6. 额外信息（调用示例）。
  → **把「评测契约」直接做成可浏览、可复制、可对照的站内文档**，而不是只放在仓库里，是提交体验的关键。

### 2.3 排行榜 `/leaderboard`（核心页面）`[实测]`

**三层下拉筛选**（页面右上角）：
1. 评测集：`official-tasks` / `Micro-official-Tasks`
2. 子集：`全部 / Level 1 ~ Level 5 / Micro-official-Tasks`
3. 算子：`全部 / Exp / SwiGlu / ApplyRotaryPosEmb / …`（全量算子名）

**筛选面板**：`硬件`（全部 / 950PR / 950DT / A3）、`版本`（最新 BETA / 2.0 BETA / 1.1 / 全部）、可折叠的「更多筛选」、搜索框 `搜索方案、任务、算子或用户…`；有筛选时出现「清除筛选」。

**KPI 条随筛选联动**：搜索 `ForgeKernel` 后，最高总分变为 `4394.66 · ForgeKernel · 950DT`、中位加速比 `1.793×（基于 1 个方案）`、通过率 `98.2%（1178/1200 测例）`、分页变 `1-1/1`。即**顶部汇总数字不是全站常量，而是当前结果集上的统计**。无匹配时 KPI 显示 `—`，表格空态为「暂无记录 · 提交算子后出现在此」。

**表格列**：`#` / `方案`（方案名 + 实现语言标签 + `59 任务 · official-tasks · 2.0`）/ `硬件` / `用户`（用户名 + 组织或「独立开发者」）/ `总分 ↓` / `平均分 ↕` / `基础加速比 ! ↕` / `理论加速比 ! ↕` / `提交算子 ↕` / `测例 ↕` / `更新 ↕`。除排名与方案外各列可点击排序，当前排序列显示 `↓`，其余显示 `↕`。行内 `NEW` 徽标标记近期更新。
实现语言标签实测出现：`CANNBot-DSL`、`AscendC`、`PyPTO-Pro`、`混合实现`、**`Triton-Ascend`**——说明平台已把不同 DSL/实现作为一等展示维度。

**行展开（重点交互）**：每行是 `expanded=false` 的可展开按钮，展开后显示
- 「聚合后的算子贡献明细」——每行对应当前聚合结果中最终生效的一项算子成绩；
- 「实现语言汇总」——按已识别的计分算子统计（如 `CANNBot-DSL 48 个算子 100%`、`已识别 48/60`）；
- 明细表列：`算子 / 实现语言 / 来源 Job（job_xxx + 2.0.0）/ 用户 / 总分 / 平均分 / 基础加速比 / 理论加速比 / 测例 / 通过比例 / 更新`；来源 Job 可跳 `/workspace/jobs/{job_id}`。

即一个「方案」的每一行成绩可能来自**不同 Job、不同用户、不同实现语言**，榜单展示的是聚合后的最佳贡献。这让「谁贡献了哪个算子的最佳实现」可追溯。

**分页**：`显示 1-20 / 44`、`20 条/页`、页码 + 上一页/下一页。

**搜索匹配范围 `[实测]`**：输入 `ForgeKernel` 命中 1 条；输入 `Triton` 返回空（尽管列表里有 `Triton-Ascend` 标签）。可见搜索字段与 placeholder 一致（方案、任务、算子、用户），**不含实现语言标签**。若要做标签搜索需显式加筛选器。

### 2.4 提交 `/submit` `[实测·登录]` + 提交规范 `[文档]`

访客态只有登录墙：「登录后提交算子。需要通过 GitCode 登录，平台才能把任务、日志和排行榜结果归属到你的账户。」+ 登录按钮。登录后 header 新增「工作台」导航，右侧变为用户名（链到 `/workspace/account`）与「退出」按钮。

**登录态提交表单（自上而下的完整字段）**：

| 区块 | 控件与选项 | 交互细节 |
|---|---|---|
| 上传 | `提交 · ZIP`、`↓ 下载示例`（指向 GitCode examples）、`↗ 查看完整提交细则`（`/docs/submission-validation`）、`选择 ZIP` 文件选择按钮（显示「未选择任何文件」） | 提示「ZIP 压缩后上限 **10 MiB**；wheel 仅接受 `dist/cann_bench*.whl` 算子包。运行时和第三方依赖需在目标 Runner 环境配置，请勿随包上传」 |
| 提交格式 | 评测集 `official-tasks` / `Micro-official-Tasks`；评测版本 `1.1.2` / `2.0.0 BETA · 推荐` | 均为分段按钮（segmented control），推荐项带 `BETA · 推荐` 徽标 |
| 目标硬件 | `A3 ×6` / `950PR ×2` / `950DT ×4` | **按钮上直接显示在线 runner 数量**，并有「当前在线: A3 ×6, 950PR ×2, 950DT ×4」实时汇总 |
| 运行环境 | 实现语言/框架 chip 多选：`ACLNN Launch / Direct Launch / CANNBot-DSL / TileLang / Triton-Ascend / PyPTO / PyPTO-Pro / 混合语言 / 其他`；`本次运行备注` 文本框 | chip 选中后为 `chip is-active` + `aria-pressed=true`；实测点选 `Triton-Ascend` 生效 |
| 聚合方案 | `combobox`「请选择有权限的方案」，option 含「＋ 创建新聚合方案」 | 标注「标准提交必选」；旁注「组织、Model、Agent、Harness 属于方案；Job Tag 只是本次运行的独立备注」 |
| 执行资源 | 说明「根据所选聚合方案、硬件和评测版本自动确认可用资源并调度」；未选方案时提示「请先选择已有聚合方案」 | 资源池由前三项联动推导，用户不直接选 runner |
| 私有提交 | checkbox（默认未勾选） | 「仅提交者和 admin 可见，不会出现在公开任务列表或排行榜中」 |
| 提交 | `提交评测` 按钮 + `剩余 10/10` + 「本次提交预计消耗 1 个积分 · 重置时间 2026/11/12 00:00:00」 | **未选 ZIP/方案时按钮 `disabled`**，即前端做前置校验；额度与重置时间实时显示 |

**「＋ 创建新聚合方案」弹窗**：字段为 `方案名称（必填）` + `方案属性：组织（必填）/ 基础模型 / Agent / Harness`，说明「方案名称用于识别和展示；组织、Model、Agent、Harness 作为方案属性，可在工作台继续维护」，按钮 `取消 / 保存并选中`。即**方案承载组织与模型元数据，Job Tag 只是一次运行的自由备注**。

> 以下为站内 `/docs` 公开的提交前校验契约（网站侧规则，与评测器侧约束分离）：

| 规则族 | 负责范围 |
|---|---|
| `WEB-ZIP-*` | ZIP 格式、资源、路径、归一化布局、扩展名白名单 |
| `WEB-SUBMIT-*` | Benchmark 版本约束、算子选择、安全扫描 |
| `EVAL-* / AUTO-* / SUB-BEH-*`（仓库侧） | 构建、接口发现、精度、性能、运行行为与反作弊 |

具体约束：压缩后 ≤ 50 MiB（**注意：线上提交页 UI 写的是 10 MiB，见 3.6**）、≤ 5000 条目、解压后 ≤ 500 MiB、路径不含 `..` 且不以 `/` 或 `\` 开头、无符号链接、路径深度 ≤ 16、文件名 ≤ 255 字符、扩展名白名单；允许 ZIP 含一层或多层共同外层目录并自动归一化；归一化后须匹配 ACLNN/direct-launch 或 TileLang/**Triton-Ascend** 两类布局之一，且根目录含 `build.sh`。`manifest.yaml` 可选且不能覆盖页面选择的 Benchmark 版本。算子名从 `cann_bench/__init__.py` 的顶层 `def` 与 `from .module import name` 识别，下划线开头不展示，且必须与当前 Benchmark schema 函数名匹配。

**错误信息格式（强推荐借鉴）**：
```
[规则编号] 问题位置 · expected: 期望 · actual: 实际 · fix: 修复建议
```
同一阶段可独立判断的问题一次性返回；前置失败（如 ZIP 打不开）阻断后续检查。

### 2.5 文档 `/docs` `[实测]`

左侧目录为分组 + 页签：`提交规范`、`提交校验`、`CLI 接入指导`、`MCP 接入推荐`、`CLI 脚本推送`、`榜单规则`、`榜单方案规则`；正文右侧还有二级锚点目录。

- **MCP 接入推荐**（默认页）：完整工具表 `get_version / whoami / get_credits / list_runners / list_runner_pools / list_benchmarks / get_benchmark_task / submit_kernel / rerun_hidden_cases / get_operator_rank / get_job / get_job_logs / list_jobs / download_aggregation_snapshot`，每个工具列出参数表 + 后端路由（如 `POST /api/submissions`、`GET /api/jobs/{id}/logs`）；含 Claude Code / OpenCode 的 `pip 安装 · 推荐` 与 `uvx 零安装` 代码切换页签、`复制给 Agent`、配置参考与常见问题（401/429/503、queued 卡住、SHA-256 去重、超时等）。
- **CLI 脚本推送**是**交互式配置生成器**：选择评测集、目标硬件（A3/950PR/950DT）、提交标签、团队聚合码、私有提交开关，下方实时生成一段可复制的 bash 提交+轮询脚本（含 `CANN_BENCH_TOKEN` 导出提示、benchmark slug、job tag、aggregation token、`PRIVATE_SUBMISSION`）。把接入成本降到「填表单 → 复制脚本」。
- **榜单方案规则 / 提交校验**两页见第 3 节。

### 2.6 动态 `/updates` `[实测]`

分类筛选导航（`role="Article categories"`）：`全部 10 / 平台动态 2 / 版本发布 6 / 评测洞察 1 / 技术文章 1`，按钮上直接带计数。文章卡：日期 + 分类 + 标题 + 摘要 + `1 MIN READ` + `阅读全文 →`。
内容本身构成**平台变更日志**：Season 2 Beta 内测、Season 1 沙龙、MCP 0.9.1（评测版本选择、执行池路由）、V1.1.2（补充 950DT 性能元数据）、V1.1.1（参考实现修复与性能基线更新）、方案对比空间与 HTML 报告导出、V1.1.0 评测完整性/反作弊升级、V1.0.0 上线、Micro Bench 与子集排行榜、CANNBench 介绍。
→ 评测集版本变更、评分口径变更、反作弊规则变更都有对外公告，这与「结果可追溯」是配套的治理设计。

### 2.7 工作台 `/workspace/*` `[实测·登录]`

访客态：`PERSONAL WORKSPACE` / 「登录后管理你的任务与榜单成果」/「Guest 用户无法访问该页面。登录后可统一查看本人任务，并维护进入排行榜聚合的最佳结果。」+「登录并继续」。

登录后左侧为固定的个人空间导航栏（5 项，均带副标题）：`任务管理 / 提交与评测进度`、`榜单管理 / 最佳结果与聚合`、`聚合方案 / 公开名称与 Owner`、`方案对比 / 聚合方案横向对比`、`用户中心 / 身份与访问令牌`；顶部有「提交新任务 →」。

| 子页 | 路由 | 功能与交互 |
|---|---|---|
| 任务管理 | `/workspace/jobs` | 统计「N 个任务」；搜索 + 状态筛选（全部/进行中/已成功/失败）+ 运行平台（全部/A3/950PR/950DT）+ 评测集版本 + 来源（非迁移/迁移任务）+ 排序（最新提交/最早提交/分数从高到低/分数从低到高）；空态「暂无任务。提交你的第一个算子」 |

## 3. 核心平台机制（对设计最有价值的部分）`[文档]`

### 3.1 版本与榜单迁移

- **中间版本**（`v1.0.0 → v1.1.0`）意味着评分细节、用例或反作弊规则变化 → 结果属于**不同评测规则体系**，榜单分开。
- **补丁版本**（`v1.1.0 → v1.1.1`）不拆分榜单；榜单统一按**前两位版本**（`1.1`）聚合与筛选，展开算子贡献后仍展示实际三位版本以便溯源。
- 版本升级后自动迁移受影响榜单的 **TOP 10**：不复制旧分数，复用原 Submission 创建新 Job，在新评测包/标准/反作弊规则下**完整重评**；迁移以低优先级调度，完成前公开榜继续展示上一版本以保证平滑切换；官方建议用户直接按新版本提交。

### 3.2 方案聚合、算子 Top1 与失效

- 排行榜以**聚合码**识别方案，聚合码全局唯一，决定哪些结果合并计算；公开榜展示聚合码绑定的 **Tag**（Tag 可重复，但一个聚合码只对应一个 Tag）。
- 提交者不能在原聚合码内单独改 Job Tag；要换公开名称须把活跃贡献**拆分到新聚合码**并在创建时设新 Tag；加入既有聚合码需管理者授权。
- **算子 Top1**：每个「方案 × 评测范围 × 算子」只保留一个最佳贡献。Job 完成时按得分排序，同分依次比较正确性、通过率、通过用例数、完成时间；落后贡献立即标记失效。Job 不再有任何活跃贡献时成为完全失效 Job，不再进入榜单/工作台/缓存重建。
- **管理权**动态归属于活跃贡献有效分总和最高的用户（平局依次比覆盖算子数、最后完成时间、Job ID），只有管理者能改 Tag。**此条为 `/docs` 的旧版规则**，线上工作台已改为「创建者固定 Owner、贡献分不改变管理权」，见 3.6。
- **异步刷新**：方案修改先持久化再进刷新队列，公开榜与工作台读同一份活跃贡献索引，界面显示「更新中」，刷新完成后同步最终排名；改 Tag 不影响得分与排名。

### 3.3 提交额度、去重与调度

- 每次提交消耗 1 个额度（每算子 1 个）；基础额度每日零点重置；完成且刷新个人最佳可 +1 bonus（跨天累积，上限 10）；**失败任务退还额度**；每用户同时最多 3 个活跃任务。
- **SHA-256 去重**：上传相同 ZIP 直接返回已有提交，不消耗额度；要重新评测必须改变内容（哪怕只是注释）。
- 维护模式（503）可全局暂停提交；`queued` 长期不动时提示用 `list_runners` 检查目标硬件是否有在线 runner。
- Runner 分共享池 / 私有池 / 独立环境；独立环境需用户显式 `independent_environment_consent_version=v1`，方案绑定本身不等于同意。

### 3.4 鉴权与 Agent 原生接入

- GitCode OAuth 登录 → Web UI「账户 → API Token」生成 `cnb_…` Token（默认 30 天、最长 3650 天、仅显示一次、服务端 sha256 存储、可撤销、绑定账户）。
- **双通道接入**：`benchsite-mcp`（本地 stdio 适配层，供 Claude Code / OpenCode / Trae 等 Agent 直接提交与轮询）与 CLI/bash 脚本（供人工与 CI/CD）。MCP 自引导升级、版本化下载地址、匿名 PV/UV 观测、不新增鉴权。
- `get_benchmark_task` 直接把 `desc_md / proto / golden_source / cases_yaml` 交给 Agent，实现「Agent-Native」的任务获取闭环。
- 隐藏测例（`rerun_hidden_cases`）、算子排名（`get_operator_rank`）、阶段日志（`get_job_logs`）、私有提交（`is_private`）、小组最佳快照导出（含 JSON/HTML 报告 + 源码，SHA-256 校验、不消耗额度、私有提交不纳入、逐环节校验权限）。

### 3.5 前端数据契约 `[缓存]`

浏览器 `localStorage` 键 `benchsite:get-cache:v1:public:display-v2:/api/public/leaderboard?version=latest&mode=solution&detail=summary` 显示：
- 榜单走公开 REST 接口，参数 `version=latest`、`mode=solution`、`detail=summary`；带 `etag`、`expiresAt`、`staleWhileRevalidateMs=86400000`（SWR 缓存 24h）。
- 返回 `total: 44`、`available_hardwares: [910c, 950dt, 950pr]`、`available_versions: [2.0, 1.1]`、`result_scope`，即**筛选项由后端下发而非前端写死**。
- 单条方案字段含 `detected_language`、`solution_tag`、`organization`、`benchmark_version` 与 `benchmark_version_source`（如 `2.0` / `2.0.0`）、`score / standard_score / hidden_score / has_hidden_eval`、`best_job_id`、`op_names[]`、`component_detail_available`、`contains_independent_environment_results`、`metric{total_cases, passed_cases, total_operators, geometric_mean_speedup, geometric_mean_speedup_vs_hw, overall_score, hardware}`、`hidden_metric`。
→ 「展示版本 `2.0` + 来源版本 `2.0.0`」双字段正是补丁版本合并展示得以实现的基础。

### 3.6 实测校正：站内文档与当前 UI 的口径差异 `[实测·登录]`

登录后实测发现，`/docs`（含 `/docs/submission-validation`）与线上表单/工作台存在多处不一致，推测是 Season 2 改版后文档滞后。**引用规则时应以 UI 实测为准**：

| 项目 | `/docs` 公开说明 | 线上 UI 实测 | 影响 |
|---|---|---|---|
| ZIP 体积上限 | `WEB-ZIP-001` 压缩后 ≤ **50 MiB** | 提交页「ZIP 压缩后上限 **10 MiB**」 | 提交前校验的实际阈值更严格；参考 4.4 |
| 提交额度 | 每次/每算子 1 额度，bonus 上限 10，失败退还，最多 3 个活跃任务 | 「剩余 **10/10**」「本次提交预计消耗 **1 个积分**」「重置时间 2026/11/12 00:00:00」 | UI 用「积分」措辞并展示实时余额与重置时刻，比文档更直观 |
| Token 有效期 | 默认 30 天、最长 3650 天 | 7 天 / 30 天 / 90 天 / 180 天 / 1 年 / **永久有效** | 实际提供更长档位，并提示「只有可信自动化场景建议选择永久有效」 |
| 方案管理权 | 「动态归属于活跃贡献有效分总和最高的用户」 | 「**创建者成为固定 Owner**；Owner 可改名、添加成员、审批申请和转让 Owner。**贡献分不会自动改变管理权**」 | **规则级冲突**，3.2 节的「动态归属」应视为旧版规则；当前以固定 Owner 为准 |
| 硬件命名 | MCP/API 用 `910b2` / `910c` / `950dt` / `950pr` | 提交页与筛选器用 `A3` / `950PR` / `950DT`，且带在线 runner 数量 | 面向用户的展示名与内部标识分离 |
| 评测版本 | `v1.0.0 / v1.1.0 / v1.1.1 / v1.1.2` 三段式 | 提交页 `1.1.2 / 2.0.0 BETA · 推荐`；榜单 `2.0 BETA / 1.1` | 与 3.1 的「榜单按前两位聚合」一致，但提交侧展示完整版本 |

> **对 Triton 平台的直接教训**：规则文档与校验实现若分两处人工维护，必然漂移。应让校验规则编号、阈值、错误文案由**同一份机器可读规则表**生成后端校验器与前端提示/文档页，并对「文档阈值 vs 运行时阈值」加一致性测试。

## 4. 对 Triton-Ascend 评测平台的借鉴建议

对照 `docs/评测体系要求.md` 的「规范—生成—运行」三层架构与「功能完备性 + 综合性能」双目标，逐条给出建议。

### 4.1 P0：应直接照搬的机制

| 借鉴点 | 建议落地方式 |
|---|---|
| **评测契约站内化** | 把 Specification、case 覆盖标签、合法输入/排除规则、编译选项、warmup 与统计口径做成站内可浏览文档页（参考「接口」页签的左侧 case 列表 + 右侧 desc + 复制 Markdown），并提供 corpus 参考包下载。 |
| **规则编号 + 结构化报错** | 定义 `WEB-ZIP-*` / `WEB-SUBMIT-*` 类似的规则族，错误信息统一为 `[规则编号] 位置 · expected · actual · fix`，同阶段错误一次性返回；网站校验与评测器约束明确分家（对照 `submission_spec.md` 已有的 `EVAL-* / AUTO-* / SUB-BEH-*` 编号体系）。 |
| **版本合约与自动重评** | 采用「中间版本分榜、补丁版本合并」规则；榜单按 `主版本.次版本` 聚合，明细保留完整三位版本；corpus 或评分口径升级时自动重跑 TOP N（不复制旧分数），重跑完成前保留旧榜并标注迁移中。 |
| **结果全链路可追溯** | 每次运行产生 `job_id`，保存阶段事件（编译 / 正确性 / 性能 / 归档）与逐 case 原始日志、重复测量数据与波动区间；榜单行的展开层能下钻到 case 级明细、来源 job、提交者、编译器版本。 |
| **KPI 随筛选联动 + 口径标注** | 顶部汇总基于当前结果集计算，并在每个指标旁标注筛选范围和口径 tooltip；避免首页全局数字与榜单数字口径不一致造成误解。 |
| **多维度筛选由后端下发** | 评测集 / 子集 / case 特性 / 硬件 / 编译器版本 / 实现后端等筛选项从 API 的 `available_*` 字段生成，不写死在前端。 |
| **提交页前置校验与实时成本提示** | 未选文件/方案时禁用提交按钮；表单内实时显示「剩余额度 10/10」「本次预计消耗 1 个积分」「重置时间」，让用户在提交前就知道代价，减少无效提交与额度争议。 |
| **在线资源可视化** | 硬件选项直接带在线 runner 数（`A3 ×6`），并给出汇总行；Triton 平台可改为显示各后端 / 编译器版本的可用执行机数量与排队情况。 |
| **规则单一事实来源** | 规则编号、阈值、错误文案由同一份机器可读规则表生成后端校验器、前端提示与文档页（见 3.6 的文档漂移教训）。 |

### 4.2 P1：按 Triton 特点改造后借鉴

| CANNBench 做法 | Triton 平台的改造方向 |
|---|---|
| 榜单单元 = **方案（聚合码）**，聚合多个 Job 的算子 Top1 | 榜单单元应改为 **「编译器实现 × 版本 × 硬件后端 × corpus 版本」**；同一编译器的不同编译选项/不同 corpus 不可混算。若需要「团队方案」概念，再引入聚合码，但主键仍是编译器 build 标识。 |
| 指标：总分 / 平均分 / 基础加速比 / 理论加速比 / 通过率 | 指标建议为 **Coverage 得分（语言特性覆盖率 ≥90%）+ Performance 得分 + 编译通过率 + 精度通过率 + 波动区间**；性能必须声明统计口径（重复次数、warmup、置信区间），不可只给单一加速比。跨编译器版本对比要单独做「提升/回归」视图。 |
| 实现语言标签（AscendC / PyPTO / Triton-Ascend） | 改为 **后端标签**（`triton-ascend` / `triton-cpu` / 参考实现等）+ **编译器版本徽标**；Triton-Ascend 应作为一等筛选维度。 |
| 提交物 = 算子 wheel/ZIP（文档 ≤50 MiB、线上 UI 10 MiB、须含 `build.sh`） | 提交物可能是编译器仓库快照 / wheel / 容器镜像，体积与布局规则需重定；但「归一化目录 + 必填 manifest + 白名单 + 安全扫描 + SHA-256 去重」的思路完全适用。 |
| 隐藏测例、私有提交、独立环境同意 | 对应为**隐藏 corpus 分片**（防止针对公开 case 过拟合）、内部编译器版本的私有榜单、第三方执行环境的显式授权，均建议保留。 |
| 聚合码管理权动态归属、Job Tag 不可改、算子 Top1 去重 | 团队/方案治理可借鉴，但编译器评测更关心「同一次 build 的多次运行取哪次为代表」——应改为**按 build 取最佳/中位运行**并保留全部运行记录，而非按用户归属动态决定管理权。 |

### 4.3 P2：运营与生态能力

- **Agent 双通道接入**：提供 MCP 工具集（`whoami / get_credits / list_runners / list_benchmarks / get_benchmark_task / submit_kernel / get_job / get_job_logs / list_jobs / 快照导出`）+ CLI 配置生成器，让 Agent/CI 能自助完成提交与结果回收；`get_benchmark_task` 应返回 case 的覆盖标签与生成元数据。
- **配额与公平性**：每日额度 + 失败退还 + 奖励额度 + 活跃任务上限 + 维护模式 + runner 在线状态首页可见。
- **公开变更日志**：corpus 版本、评分公式、精度阈值、反作弊规则、编译器兼容矩阵的每次变更都发公告（参考 `/updates` 分类筛选），并保留历史版本榜单入口。
- **报告与对比**：JSON + 自包含 HTML 双格式；增加「方案/版本对比空间」，支持导出带 SHA-256 校验的快照 ZIP（含报告与源码，权限逐项校验，不消耗配额）。
- **登录与讨论**：OAuth 接入代码托管平台，把任务、日志、榜单归属到账户；页面固定悬浮「问题讨论」入口承接社区反馈。

### 4.4 明确不建议照搬的点

- `50 MiB / 10 MiB / 5000 条目 / 扩展名白名单` 等具体数值是算子 wheel 场景的产物（且平台自身文档与 UI 已不一致，见 3.6），编译器提交物需重新评估，切勿直接抄数值。
- 「方案管理权动态归属活跃贡献最高者」属于旧版规则，当前线上已改为创建者固定 Owner；若借鉴团队治理，应先确认目标版本，避免把已废弃规则写进自己的规范。
- 「基础加速比 vs 理论加速比」依赖 CANN 的硬件锚点 `T_HW` 模型；Triton 项目若没有等价的硬件理论上界，不要硬造同类指标，应改用可解释的基线对比 + 波动区间。
- 首页「最高分 8591.8」与榜单「最高总分 4495.33」口径不一致的问题应在自己平台中避免：所有全局 KPI 统一标注数据范围与版本。

- **仍未实测**：真实提交与任务生命周期（**刻意不点「提交评测」**，避免消耗额度、占用真实 NPU runner 并污染公开榜）；有任务数据账号的工作台列表与阶段日志（本次账号 0 个任务）；方案对比的实际结果矩阵与 HTML 报告导出（遇 `503 display query capacity reached`）；Token 实际生成（不创建凭据）；方案拆分/Tag 修改/批量修改、隐藏测例触发、快照下载。这些仍以 `[文档]` 标注。
- **观察备注**：点击「更多筛选」时曾短暂出现全空态（`—` / 暂无记录），刷新后恢复，判断为数据刷新竞态而非设计特性；「夜间」菜单项可见但本次未验证切换后的视觉效果；访问他人 job 详情页停在「加载中 · 任务」，可能是权限边界也可能是加载态缺陷，需有数据账号复核。

### 5.2 可直接复用的界面文案

- 空态：`暂无记录 · 提交算子后出现在此`、`暂无提交 / 成为第一个提交者`
- 状态提示：`更新中`、`NPU runner 就绪`、`阶段 · 空闲`、`当前无运行任务，提交算子后可在此实时查看评测过程`
- 搜索 placeholder：`搜索方案、任务、算子或用户…`
- 引导四步：`从任务规格开始 → 提交算子实现 → 在 Ascend NPU 上运行 → 在排行榜上比较`
- 榜单展开标题：`聚合后的算子贡献明细 / 每行对应当前聚合结果中最终生效的一项算子成绩`、`实现语言汇总 / 按已识别的计分算子统计`
- 提交表单提示：`ZIP 压缩后上限 10 MiB；wheel 仅接受 dist/cann_bench*.whl 算子包`、`当前在线: A3 ×6, 950PR ×2, 950DT ×4`、`组织、Model、Agent、Harness 属于方案；Job Tag 只是本次运行的独立备注`、`仅提交者和 admin 可见，不会出现在公开任务列表或排行榜中`
- 成本与额度：`剩余 10/10`、`本次提交预计消耗 1 个积分 · 重置时间 …`、`请先选择已有聚合方案`
- 工作台说明：`方案名决定榜单展示；聚合 ID 由系统生成且不可修改`、`创建者成为固定 Owner；Owner 可改名、添加成员、审批申请和转让 Owner`、`仅同评测集、同版本、同硬件的方案可对比`、`点击行选择 2–5 个方案；翻页不会丢失选择`
- 限流降级：`HTTP 503: display query capacity reached`（表内错误文案 + 相关控件禁用，而非白屏）

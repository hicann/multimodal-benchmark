## 0. 对照覆盖报告后的基线修正

已通读 `docs/requirements-coverage-report.md`，并核对构建脚本、规格、参考自检、
参考加载、比较器、监督者和评分代码。此前方案没有充分区分“已有”与“待补”，
以下分类优先于后文的目标性描述。覆盖报告的主要实测基线是 v0.5，
其成熟机制需要逐项核对 v0.6 是否接入，不能直接将两者状态等同。

不作为修复 v0.6 的前置条件，不直接改变已确认的评分口径。

本轮优先级收敛为：v0.6 语义与实现修复 → 已有生成/门禁接入 → 参考资产补齐
与比较器边界修复 → 能力归因与设备故障隔离增强。结果反哺生成可后续扩展，
网站、榜单和规模扩容按覆盖报告单独推进，均不是本轮数值失败的直接解释。

## 1. 目标与基本边界

目标是在同一份客观题库上，既能评价用户上传实现是否正确、是否快，
也能把具有独立证据的编译器能力缺口交付给编译器开发方。

保留现有生成、选择、校验、执行和评分机制，补齐共同约束与质量门禁。
不为每个来源仓库另建一套评测流程，也不按某份示范实现的通过情况挑选正式题库。

需要明确区分三件事：

1. **算子语义合法域**：数学定义和接口允许什么输入、输出与近似行为。
2. **运行资源预算**：平台事先声明的内存、时间、设备条件。
3. **实现/编译器能力**：特定代码或工具链能否完成上述合法问题。

示范代码固定的 BLOCK_SIZE、当前编译器不支持的 dtype，不能成为偷偷缩小语义合法域的理由。
平台资源确实容纳不了的负载，可在发布前定义统一预算并披露未覆盖范围；不得运行后按提交成败裁题。

## 2. 先把“失败阶段”和“责任归因”分开

`COMPILE_FAIL` 说明编译阶段失败，不自动证明是编译器缺陷。
错误 constexpr、非法 DSL 调用、示范包装器缺陷也可能产生 Triton CompilationError。
同样，WRONG_RESULT 既可能来自内核，也可能来自错误参考、未定义契约或受污染的设备会话。

保留现有 CaseStatus，新增独立诊断记录；不要为了责任分类不断扩张终态枚举。
诊断记录至少包含 stage、reason_code、suspected_owner、confidence、evidence、repro_id：

- stage：input / oracle / compile / execute / compare / measure / supervisor。
- suspected_owner：contract / corpus / oracle / submission / compiler / environment / unknown。
- confidence：suspected / reproduced / confirmed。
- evidence：异常类型、实际张量元数据、分输出误差、版本、日志和复现链接。

不能按异常 message 自动给出“编译器已确认缺陷”。诊断更新保留历史和依据，
不覆盖原始观测记录；修订责任不等于随意重写旧分数。

| 观测与证据 | 处理 | 对用户评分的影响 |
|---|---|---|
| 输入违反已发布语义约束 | SPEC_ERROR，修复构造或规格 | 不扣用户；受影响范围暂缓正式分数 |
| 参考失败、参考互相矛盾 | ORACLE_FAIL，隔离参考问题 | 不扣用户；禁止静默缩小分母后排名 |
| 用户实现违反输出/输入保护契约 | SUBMISSION_INVALID，规则明确定位 | 该范围不具备正式评分资格，不能靠排除坏例获高分 |
| 合法输入上用户实现编译/执行/数值失败 | 保留对应失败终态 | 固定范围内计失败；原因可继续诊断 |
| 合法 DSL 的独立最小复现仍失败 | 记录 compiler 候选缺陷及支持矩阵 | 能力失败保留，不因“不支持”改成 PASS 或从分母消失 |
| 设备故障、进程异常后上下文不可信 | ENV_ABORT/未执行，重建环境后补跑 | 不把受污染会话的后续结果当作独立数值缺陷 |

## 3. 统一算子契约：类别负责归类，语义身份负责判题

用户仅选择 Elementwise、IndexGather 等 category 不足以确定答案。
提交必须绑定具体 operator_id、contract_version、entry；category 和 level 由注册表提供。
例如 Gather 与 Scatter、加权与不加权重排不能因为同属 IndexGather 就共用一个模糊签名。

在现有 `operatorspec.py` 基础上逐步补充可验证契约：

| 项目 | 必须表达的内容 | 执行位置 |
|---|---|---|
| 参数 | 张量名、顺序、可选项、属性默认值/枚举/范围 | 加载与构造前 |
| 多输入关系 | 每个张量 shape/dtype，跨张量维度关系、索引范围 | 输入生成后、实现执行前 |
| 输出 | 固定结构、各输出 shape/dtype/device、布局约束 | 参考自检与实际返回后 |
| 更新与别名 | 默认输入只读；状态更新返回新状态；允许的输出别名需显式声明 | 参考与提交分别检查 |
| 边界语义 | 空输入、空 split、padding、重复索引、越界索引、并列结果 | 规格和针对性用例 |
| 数值语义 | 累加/舍入要求、允许近似、非有限值策略 | 参考和逐输出比较 |
| 负载描述 | 主张量 shape 与逻辑参数分开，工作量估计 | 标签、规模分档、资源预算 |

采用显式注册、带单元测试的语义校验函数处理复杂关系，不将任意字符串表达式交给 eval。
全局只检查通用结构，算子插件负责具体关系；生成和运行调用同一个校验入口。

负向接口测试单独成套，验证非法输入是否按契约拒绝，不混入正常数值题库的分母。
未定义行为不能靠某个参考实现的偶然输出生成标准答案。

新语义版本统一决定 VectorCmp 是否返回三个张量、GatherScatter 系列是否加权、
空注意力 split 的中性值以及 CausalConv1d 的状态返回方式；历史版本保持可解释。

## 4. 参考实现：独立、可复算、验证所有输出

将 v0.6 的输入构造和数学参考与教程加载解耦。
纯 torch/NumPy 参考应能在 CPU 独立执行，不因为被测 Triton 导入失败而全部消失。
CausalConv1d 的数学参考从教程依赖中独立出来，保留出处并做小规模手算对照。

参考分工：

1. 数学参考是判题依据；小规模使用 CPU 高精度作为交叉锚点，检查实际计算 dtype。
2. 同设备参考提供规模可承受的执行及性能基线，需要先与数学参考交叉认证。
3. 模拟 bf16/fp16 中间舍入或 online softmax 的参考仅用于诊断；不能因复刻了
   被测内核而自动成为唯一真值。容许哪些近似由契约决定。

参考发布门禁应检查：

- 输入构造满足全部语义约束；同 seed 可复现，独立生成两次也得到相同输入。
- 输出结构、元数、每个张量 dtype/shape/device 都符合规格；不只取第一个输出。
- 两次参考调用使用独立输入副本；检查输入未被修改，并避免返回别名导致伪确定性。
- 所有输出符合有限值策略；padding、未激活分区和更新状态也参与检查。
- 小规模两个独立算法交叉一致；难以全量高精度验证时披露抽样范围。
- 注册适当的性质测试，例如 gather/scatter 逆变换、输入置换等价、状态递推等价。
  性质必须带前提，不能泛化成所有算子都满足同一关系。

任何参考失败使该算子版本暂缓发布，不能简单“剔除失败例后覆盖率仍达标就冻结”。
已有语料发现坏题时发布勘误并给出受影响范围；同一修订对所有用户一致重评。

## 5. 数值比较与容差：按输出语义制定，按证据标定

继续使用集中容差策略，禁止提交方指定自己的宽容差和逐 case 开后门。
增强为按 contract、输出名、输入 dtype 组合、数学上有意义的规模区间选择策略；
这些区间和阈值必须在正式运行前版本化，独立于提交代码和实际失败 case ID。

不能把 `max_rel/max_abs` 聚合诊断量、各输出不同尺度和最终布尔判定混为一体。
普通浮点使用明确的逐元素规则；整数/布尔精确比较，不能先转 float64 再判断 int64，
超过 2^53 的整数差异会丢失。排序并列、概率归一化等需要语义比较器时单独登记。

具体比较要求：

- 每个输出独立取容差，再合并为用例结论；首个输出的 dtype 不能控制整数索引的容差。
- 有限参考对非有限提交必须失败，不能伪装成 SHAPE_MISMATCH。
  若某契约允许 NaN/Inf，检查位置和 Inf 符号，有限位置继续正常比较。
- 对空张量、零附近值、大数、整数边界分别测试比较器。
- 同时用多种合法实现、多 seed 和刻意错误的反例标定；反例应覆盖漏时间步、
  错行步长、少输出、错误权重、错误状态等。合法实现不能被误杀，反例必须被拦截。
- 独立参考之间尚无法达成已声明精度时，标为参考待认证；先解决语义或参考问题。

v0.6 注意力先修空 split 和参考索引关系，再区分 att_out、att_lse 的误差。
本轮约 1e-3 的差异提供调查线索，不能直接当作批准放宽容差的充分证据。

## 6. 生成机制：统一入口、合法性门禁与覆盖证据

保留现有功能引导、`label_case` 和 `guided_selection`。v0.6 接入同一流水线：

```text
版本化契约 + 场景/功能目标
  → 参数化候选池
  → 规格静态校验 + 构造后关系校验
  → 参考认证（昂贵部分分层执行）
  → 纯函数标签 + 负载规模
  → 现有覆盖引导选择 + 语义组合保底
  → 已选集全量门禁 + 覆盖复核
  → 发布冻结包
```

候选池大时，先对每种新构造模板和边界类型做小规模参考认证，选中集再全量检查。
最终门禁失败则停止发布并修复/重新生成候选、重新选择，记录排除原因和覆盖缺口。
整个过程中禁止用示范实现 PASS 率作为候选合法性过滤条件。

选择约束从“数量足够”扩展为：

- dtype、实际负载规模、布局和每个关键属性至少有代表。
- 功能场景有明确的输入关系、语义目标与断言；覆盖到 dtype/shape 标签并不证明功能已验证。
- 增加有风险的交互组合，例如小 D×大 BLOCK、seq_len>1×状态更新、
  split 数大于有效块数、padding×权重、负载尾块×非连续布局。
- 公开有界组合覆盖目标，不声称有限题库覆盖全部参数笛卡尔积。
- 确定性处理并列选择；生成两次产生同一清单哈希，说明哪些参数仅改变 seed 不计新覆盖。

标签继续只依赖契约和用例，不读取用户源码。语义覆盖与实现实际触发的 DSL 路径分别披露：
同一个 gather 语义可由 pointer load 或 tl.gather 实现，不能仅凭语义通过就声称验证了后者。

功能/覆盖不足时反馈补候选；参考不可信时反馈修评测资产；实现失败反馈缺陷诊断。
这三个反馈方向必须分开，否则引导机制容易退化为自动挑容易通过的题。

## 7. 编译器能力：增加独立探针，保留真实失败

现有环境健康探针回答“工具链能否基本工作”，保留它。
另增加少量独立能力探针，回答具体 API×dtype×参数形式是否可用；
与已有优化收益探针分别命名和报告，复用已有采集与归档设施。

首批针对本轮疑点：`tl.gather(int32)`、动态/静态 extract_slice、
insert_slice 的 offsets、bf16 dot 概率转换及 UB 超预算边界。
每个探针固定源码、输入、预期结果、后端约束和资源预算，独立进程编译执行。

支持矩阵按设备、驱动、CANN、torch/torch_npu、Triton 包/源码提交、
编译选项和探针版本存档；“均显示 3.2.0”不构成环境完全相同。
状态使用 pass / fail / not_tested；异常中断不冒充确定的不支持。

探针作用是解释和复现，不是按探针结果删除正式用例：

- 对用户实现：合法域内失败仍是该固定环境下的提交失败，明确披露环境限制。
- 对编译器：用受控、已验证合法的探针独立归因。用户某段代码失败但探针通过，
  只能说明仍需调查；探针失败也不证明所有同语义实现都会失败。
- 用户声明支持范围只能形成事先定义的分轨。全功能轨不允许运行后自行跳过难例。

数学上合法不等于符合后端 DSL 的已声明前置条件。探针需要同时记录后端文档约束：
违反已有约束属于调用问题；文档明确不支持属于能力缺口；承诺支持但合法最小程序失败
才进入编译器缺陷确认流程。文档不清楚时保留 unknown，并记录待确认问题。

编译器对照实验固定源码和用例，仅切换编译器；实现对照实验固定编译器与题库，
仅切换提交实现。原始教程、修订示范和用户提交有不同实现身份，不混成一条趋势线。

## 8. 运行隔离、产物与评分公平性

保留父进程监督、逐用例事件和落盘。新增的关键边界是设备上下文隔离：

- 默认正式正确性评测至少按算子启动独立 worker；已知危险、未信任或复现用例
  可以逐 case worker。进程隔离不能保证设备级故障已清除，故还需健康复核。
- 非法访存/设备断言/硬超时后终止受污染 worker，按平台支持方式重建设备上下文；
  恢复失败则暂停该设备，剩余用例标未执行并留待补跑。
- 只对环境性失败做有上限重试，保留每次 attempt；数值失败不能自动重试到 PASS。
- 参考和提交使用独立输入副本；参考判题置于独立进程边界，避免提交修改其计算/比较依赖。
- 对数据相关输出分配，例如 padded_bins[-1]，明确允许的标量元数据读取与计时范围；
  不笼统放行核心计算回 CPU，也不能把合法的输出分配误判为代算。
- 性能在正确性门禁后单独会话采集；状态算子每个样本使用等价初始状态，
  明确克隆/分配是否计时。参考基线质量和计算精度必须同语义，保留现有同会话测量。

worker 进程用于故障隔离，不能单独充当用户代码的安全沙箱。对外上传评测还需使用
平台可支持的容器/虚拟机及设备访问策略，限制网络、文件、进程和资源访问；
答案、隐藏用例和评分进程不放入提交可写的目录或可修改的进程空间。
公开输入构造分布、契约和样例，正式评测使用独立 seed 的隐藏样本；隐藏样本同样
经过认证并在本轮各提交间保持一致，留存可审计快照。不能用猜测用户是否硬编码
代替实际隔离和独立样本检验。

完整性对账继续使用已补工具；还需把 meta→case→done、清单哈希、run_id、
逐例日志和退出状态一起校验。220 行不能单独证明 220 个内核都执行过。
心跳归档必须采集正在写入的本轮结果及日志，最终归档再原子写入完整清单；
不能只上传“流程结束后才复制”的结果文件。

现有按算子加权、严格通过率以及全对后逐算子性能评分予以保留。
以下是对外正式排名的发布资格增强建议，不代表现有规范缺少评分机制：

1. 对每个注册算子版本，在执行前固定待测用例集合与权重。
2. 有数据完整性、评测方参考/规格错误或未恢复环境故障的范围，只出暂定诊断；
   展示已确认范围，但不能静默删去这些用例后参与正式排名。
3. 对已声明提交范围内的合规性失败，应明确该算子无正式分或不合规，
   不能因当前 NON_COUNTED 规则自动把难例排除而抬高正式分数。
4. 部分算子提交可以保留逐算子分数，同时列出覆盖清单；
   局部范围与完整范围不能直接横比。全量榜单按预先规定范围验收。
5. 编译失败、不支持和结果错在合格题库内均计功能失败；性能只对正确范围出分。
   各算子严格门槛和性能锚点继续披露，不跨环境/语义版本混用。

现有 anchors 已要求该算子题库用例全部 PASS 才给该算子正式性能分，
scorer 的通过用例几何平均统计与该正式分是不同字段，应保持这种区分。
预热、同步、重复测量、中位数和离散程度记录也已实现；进一步自动核验负载/频率、
对不稳定测量设置正式资格与重测规则属于增强建议，不凭一次最快值评分。

这些是新评分规范建议，需要升级 scorer_version，不能悄悄改变现有历史分数。
诊断中疑似实现/编译器责任不影响客观通过记录；真正坏题则统一勘误与重评。

涉及数据 schema 时使用显式版本和兼容读取：

- 先用独立诊断/资产清单保存新增证据，保持旧 JSONL 可读取；
  新 contract/scorer/corpus 版本再启用更严格的必填项和正式资格规则。
- 发布包绑定参考源码、输入构造、比较器、容差、标签器及相关外部依赖的内容哈希；
  case 内容身份仍独立于用户实现，整轮身份再绑定提交快照和环境。
- Store 对同一 corpus version 的不同 manifest hash 拒绝覆盖，要求新版本。
  历史评分/报告明确标识原版本，重算记录保存来源和新规则。

最终验收不以“示范 220/220”作为唯一标准，而要求：

1. 已修示范通过其声明语义域的回归；尚未支持的受控能力探针真实报告失败。
2. 合法外部实现通过，错误实现被拦，缺参考/非法输入不会冒充用户数值错误。
3. 固定范围内记录齐全、判定可复现、责任有证据、正式分数不受动态删题影响。
4. 新增一个算子只需登记契约插件、参考、候选和性质/反例测试，
   无需修改核心比较器、选择器和评分器来照顾其具体实现。

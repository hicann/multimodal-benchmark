## 覆盖率的含义和变化

覆盖率按冻结集全部用例的 `feature_atoms` 取并集，再除以完整 active 标签清单。
它不是按算子或类别分别计算后取平均，也不是用例通过率。

- 上轮真实 NPU 冻结集：50/1000，33/71 = 46.48%。
- 本轮真实 NPU 冻结集：50/1000，49/71 = 69.01%。
- 相同冻结规模下新增 16 个标签，提高 22.53 个百分点。
- 若比较完整 68 算子候选池，则是从 34/71 升至 49/71，提高 21.13 个百分点。

本轮实际冻结选择没有丢失可获资格候选所能触达的标签。该结果验证了新增输入分布、布局、
shape 分层和覆盖引导选择能够保留更多标签，并不代表已经满足任务书的 90% 要求。
按现有 71 项清单至少需覆盖 64 项，目前还需要增加 15 项不同标签。
现有清单也不能自动视为已获双方共同确认。

现有 `FA-PROG-GRID*` 是从输入 rank 派生的静态代理标签，不能证明内核采用了对应维数的
launch grid；pattern 标签同样不证明编译器实际采用相应优化。因此 69.01% 只应称为
静态语义标签覆盖率，不是执行期 Triton API、IR 或指令覆盖率认证。

## 两个失败用例和归因边界

失败均为 FloorDiv 的 int32 边界输入：

- `official-floor_div-int32-03-boundary-c`：连续主输入。
- `official-floor_div-int32-03-boundary-s2`：逻辑值相同、主输入步长为 2。

其余 18 个 FloorDiv 用例通过。两个失败均通过了 CPU 与 NPU 参考门禁，结果完整性与环境检查
也通过。它们来自同一数值边界而有不同存储布局，说明不能靠删除跨步测试来解决问题。
现有 kernel 使用整数 `//`、`%` 及符号修正求 floor。int32 极值要求精确保留整数信息，
不能把 quotient/remainder 的精度寄托于可能采用浮点近似的后端实现。

原日志仅保存 WRONG_RESULT，没有保存期望值/实际值逐元素差异，因此本报告不声称已经确定
编译器内部的具体错误位置，也不虚构硬件输出。已确认的错误范围是提交的整数除法路径
未通过上述边界用例；修复避开该路径，仍需 NPU 重新编译和执行来确认。

## 修复内容与验证范围

模板与示例提交同步添加 `_floor_divide_int32`，使用 uint32 幅值和 32 步二进制长除法，
最后恢复商的符号，并对异号且非整除的情况向负无穷取整。
uint32 能精确保留 `abs(INT_MIN)=2**31`；迭代中的余数不会超出 uint32 范围。
算法不依赖浮点转换、整数除法或整数取模，不调用主机框架代算。
原有除数非零及 `INT_MIN / -1` 排除规则继续适用。

新增测试直接提取实际 kernel helper 的 AST，在保持 32 位数值语义的 NumPy 适配器上执行，
与独立的 int64 floor_divide 比较，覆盖整数上下界、双方符号、整除与非整除、30000 对随机输入，
以及原冻结的全部 20 个 FloorDiv 用例。另增加真实 NPU 回归测试，覆盖全范围边界与正负除数，
分别验证连续和 stride=2 主输入。
这些 CPU 检查不能替代 Triton 编译与 NPU 执行；32 步展开的编译代价和性能也需要真机测量。

本地完整回归为 **684 passed、165 skipped**（117.58 秒）；跳过项包括真实 NPU 回归。

## 选择策略

先锁定原有 1,360 个用例，再从合法候选中选取缺失标签的载体。候选池共有 65 个用例，不同候选有实际的 dtype、轴、布局、shape 或属性差异；只改 seed 不算第二个独立结构见证。

选择器依次优先考虑首次补齐的标签数量、加强缺失标签见证的数量、已选算子负载、输入规模和稳定编号。对候选池可补齐的每个原先缺失标签，要求两个不同结构的用例。每个新增用例必须补标签或提供所需的第二个见证；达到见证要求即停止，不填充配额。新增总上限 64，每个算子上限 16；预算不足或无法达到 90% 都直接失败，不缩分母。

| 补充载体 | 用例数 | 实际考察内容 |
|---|---:|---|
| Scatter | 2 | int64 更新、不同轴、碰撞加和及未写位置保持 |
| Cummin | 2 | 不同轴、前缀最小值及相等最小值的索引规则 |
| GroupedMatmul | 2 | 不同浮点类型、分组列表、bias、静态循环考察负载 |
| CrossEntropyLoss | 2 | mean/sum、ignore_index、稳定 log-sum-exp |
| MaskedSoftmax | 5 | BF16、不同轴、实际 int8/uint8 mask 输入 |
| ApplyRotaryPosEmb | 2 | 连续半分和交错旋转两种模式 |
| Transpose | 2 | 不同 shape 的实际 int16 数据输入 |

int8/uint8 标签来自实际 mask 输入，不表示主数据张量是该 dtype。独立 Torch 与 NumPy/标量参考分别实现语义，新增输入构造显式保证合法关系；冻结前对全部 1,377 个用例执行独立参考交叉检查。失败不筛掉、不降容差。生成日志采用已有的带时间戳、追加事件格式，并在新版本冻结时锁定。

仍缺失四项：`FA-PAT-MULTIPASS-REDUCE`、`FA-PAT-SCAN-BLOCKED`、`FA-PAT-SPLIT-K`、`FA-PAT-VEC-BROADCAST`。保留它们在分母中。本轮用较少、可交叉校验的补充先达到启动阈值，没有为了 100% 盲目加入大负载。

## 三种覆盖口径与证据边界

| 指标 | 分子 | 分母 | 得出结论的位置 |
|---|---|---|---|
| 静态标签覆盖 | 冻结用例标签并集 | 原有 71 项 active 清单 | 本机重算 |
| 编译见证覆盖 | 同一环境中，有真实编译负载见证且满足对应特性证据条件的标签并集 | 同一 71 项 | 真机结果离线审计 |
| 执行验证覆盖 | 编译见证成立，且同步完成、该用例 PASS、CPU/NPU 独立参考门禁通过的标签并集 | 同一 71 项 | 真机结果离线审计 |

编译见证覆盖针对冻结特性义务，不能解释为全编译器 API、IR 操作、分支或机器指令的覆盖率。报告另列真实观察到的 IR 操作清单；没有双方确认的 API/IR 分母时不计算其百分比。

正确性执行期间临时采集 `JITFunction.run` 返回编译对象中的 IR 和后端产物，归档源码、编译参数（可获得时）、特化哈希（可获得时）、显式 grid、输入 dtype/shape/stride、用例哈希、清单哈希和 run_id。产物压缩并按内容去重，每个文件都有 SHA256；编译器缓存命中明确记录为编译对象见证，不声称每次都重新执行前端。每轮使用独立编译缓存目录。采集钩子在性能测量前恢复，smoke 运行本身不证明性能验收通过。

审计必须核对完整清单、评测资产、提交快照、实际内核源码、监督者产物索引、子进程完整性、环境与健康探针、每条结果及参考门禁。缺失、重复、哈希不一致、混用环境或部分算子运行均不能宣布整轮达标。WRONG_RESULT 即使产生了编译产物，也不给执行验证分。

实现类标签采用额外证据规则，例如 DOT 要求捕获的 IR 包含 dot，累加要求 atomic IR，静态展开要求内核源码和无循环 IR。原有 GRID 标签按输入 rank 推导，不能直接作为启动维度证据；真机审计要求显式实际 grid，GRID4D 保持未验证。所有优化 pattern 和中间结果消除标签暂不凭形状或 PASS 自动认证，需要专门的实现、内存或性能证据。

按当前保守判据，67 个静态已覆盖标签中，4 个优化 pattern 标签、GRID4D 和中间结果消除这 6 项尚不授予实现覆盖分，当前编译与执行覆盖的理论上限为 61/71（85.92%），实际还可能因 grid、编译或结果问题更低。要达到至少 64/71，后续必须为至少 3 个当前尚无实现判据的标签建立并通过可信真机见证，或补齐其他缺失特性的真实负载与判据；不能仅增加同类用例。

因此本轮 94.37% **不承诺**下一轮编译和执行覆盖必然达到 90%。新机制会列出未验证项、原因以及每项获分标签的用例见证。后续依实际真机缺口补齐实现证据与负载，禁止把未验证项直接算成已覆盖。

任务书要求的是“不少于 1,000 个可复现 case，覆盖双方共同确认的核心特性清单至少 90%”。仓库尚缺这份 71 项清单已经共同确认的证据，且其中含结构代理。报告保留 `AWAITING_JOINT_CONFIRMATION`、`taskbook_accepted=false`；当前结果证明本版本通过仓库现有静态口径的启动门槛。

## 复核与运行

本机使用已安装项目依赖的 Python：

```bash
python3 scripts/check_coverage_readiness.py
python3 -m pytest -q tests/test_coverage_generation.py tests/test_coverage_evidence.py
```

生成器不会覆盖已冻结版本，重跑会验证指纹及选择结果：

```bash
python3 scripts/build_coverage_corpus.py
```

真机取得包含本轮变更的提交后，在仓库根目录运行：

```bash
bash scripts/coverage-suite-verify.sh
```

该入口先验证静态门槛，再执行环境准备、参考门禁、分算子运行和覆盖审计，沿用已有结果持久化流程。`TRITON_EVAL_PREFLIGHT_PYTHON` 可指定预检 Python；默认优先使用评测 venv。正式评测仍要求 Python ≥3.11。本机 CPU 验证使用 Python 3.9.6，不等于正式环境认证。

真机结果可重新审计：

```bash
python3 scripts/audit_coverage_results.py --results /path/to/record/evidence
```

报告为 `coverage-validation.json`，包括静态、编译、执行三套结果，缺失标签、逐特性用例见证及证据哈希。只有证据完整、全部用例正确、编译和执行覆盖都达到 90%，真机覆盖达标检查才返回成功。测试中的合成证据只验证程序判定分支，不能作为真机记录发布。

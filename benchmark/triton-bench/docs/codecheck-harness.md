## 一、控制器与修复器分离

控制器读取冻结清单，分派任务、执行检查、保存证据并派生状态。Codex 作为修复器提交代码、解释和候选结果，不能自行改写控制器账本、规则阈值、验证器或例外审批。

实际执行时，冻结输入与审批记录由用户／CI 保管；修复器只对被分派的代码目录有写权限。若 Codex 与控制器共享全部写权限，本地哈希不能抵御刻意同时修改数据和验收程序，不能宣称有密码学意义的防篡改保证。

建议状态目录：

```text
baseline/        原始输入、稳定 issue_id、路径和冻结回执
tasks/           确定性逐文件任务包；跨文件问题另建关联任务
events/          控制器追加的状态事件；旧事件不可覆盖
evidence/        检查命令、工具版本、原始 JSON 输出、退出码和哈希
reviews/         人工审阅的验证器映射、依赖变更和例外审批
remote/          同版本 CodeCheck 全量复扫及新问题清单
reports/         根据上述资产重新计算的进度、阻塞和最终结论
```

事件至少记录 `event_id`、`issue_id`、前一事件哈希、原状态、新状态、代码快照、证据引用和时间。控制器使用锁与原子写入，读取时验证事件链；损坏或截断必须报错。任务租约超时只回收任务，不更改问题验收状态。

## 二、先核验现状，再实施修复

不得对 5954 条问题盲目重改。先为每种服务端 `ruleId` 建立经审阅的验证适配器，明确原规则、工具／规则版本、阈值、扫描范围及匹配策略。

现状核验只产生三种结果：

- `PRESENT`：当前代码仍违反规则，需要修复。
- `LOCAL_CLEAR`：本地对应规则未再检出；等待语义回归和服务端复扫确认，不宣称远程已消除。
- `UNKNOWN`：规则、语义或检查能力不足，作为阻塞项保留，不能等价于未检出。

不同工具的同名指标不能直接等价。例如圈复杂度、NBNC 行数和嵌套深度须匹配原门禁定义；无匹配工具时保留 `UNKNOWN`，提交服务端复扫。Ruff 只支持其实际覆盖的规则，不能用 Ruff 清零代表全部 CodeCheck 规则清零。

检查命令必须由控制器执行，记录命令、工作目录、工具版本、标准输出、标准错误、退出码和超时。Ruff 等工具使用 JSON 输出；非零退出、JSON 损坏、模式错误、工具缺失、分页缺失均不可解释为零缺陷。适配器必须区分“有诊断”和“工具执行异常”的退出码。

原工作清单以路径文本代替规则名的重复代码问题，必须从原始接口明细恢复 `ruleId` 和涉及文件组；未知前不能自动通过。目录规模规则也要独立验证，不能以“不是文件”跳过。

## 三、任务分派与修改约束

按路径字典序生成任务包，每个包包含该路径全部非文件头问题、原始上下文、当前源码指纹、必需验证器、关联依赖和验收标准。先完成一个小批次，再扩大范围；不要一次机械替换全部仓库。

建议顺序：格式／导入等低风险规则 → 内部命名 → logging 与公开入口 → 复杂度和长函数 → 跨文件重复代码与目录规则。同文件全部问题共同验收；跨文件问题不能拆成互不关联的“单文件已完成”。

修复器逐条回报 `issue_id`、是否修改、修改位置、说明、关联测试和剩余疑点；不允许自由文本 `done` 直接改变状态。不再适用的问题（例如 JSONL 迁移后路径消失）需要迁移关系和新路径验证，不能当作天然消失。

必须保留以下边界：

- 不回滚已有 license／有效质量整改，不批量添加新的屏蔽注释或降低规则阈值。
- 不破坏公开函数签名；内部参数重命名必须做作用域检查，防止维度、索引、指针同名覆盖。
- logging 改动保留 stdout／stderr、输出格式和错误传播，不能仅把 `print` 改为 `logging.info`。
- 不修改评分、容差、输入合法性和用例身份来换取通过；冻结资产若确需更新必须有显式新修订和可追溯迁移。
- 不为消除告警而修正、删除故意非法的对抗样例。需要更改测试夹具构造方式或申请例外时，保留原测试目的并经用户审阅。
- 模板、生成器、生成产物和认证器一起检查；避免只改产物导致下次生成恢复问题。

## 四、问题级状态与独立验收

非文件头问题使用以下状态：

```text
UNASSESSED → PRESENT → PATCH_PROPOSED → LOCAL_VERIFIED → REMOTE_VERIFIED
     └────→ LOCAL_CLEAR ───────────────→ LOCAL_VERIFIED
任意非终态 → BLOCKED／EXCEPTION_REQUESTED
EXCEPTION_REQUESTED → APPROVED_EXCEPTION（仅外部审批）
已验证状态 + 证据失效 → STALE（重新核验）
```

`LOCAL_VERIFIED` 必须同时具备适用规则检查通过和对应行为回归通过。适配器声明精确依赖集合；格式／AST 检查至少绑定完整当前文件，重复代码检查绑定相关文件组，目录检查绑定目录成员清单，集成回归绑定仓库快照。源码、依赖、工具版本或验证器变化，相关证据变为 `STALE`，不能复用旧通过结论。

公开入口变更需加载／契约测试；计算内核和 Triton 模板变更需真机结果；评分／报告变更需端到端结果。旧代码的真机证据不能自动证明新代码通过；不同版本或测试范围不得静默叠加为全量通过。

`APPROVED_EXCEPTION` 必须含具体问题、理由、风险、替代测试、审批人、审批时间和适用版本。修复器只能提出申请，不能自己批准。最终分别展示修复数与例外数；有例外就不得说“所有缺陷均已修复”。本地审批也不自动等价于 GitCode 服务端接受豁免。

## 五、服务端复扫与最终闸门

发布候选提交前完成本机完整回归；真机验证使用已有脚本，按变更影响范围先小量再扩展。最终 CodeCheck、回归与真机证据必须对应同一候选代码版本。检查远程扫描的提交、分支、扫描范围、启用规则与阈值没有被静默缩减。

原始 5954 条义务守恒：

```text
5954 = REMOTE_VERIFIED + APPROVED_EXCEPTION + 所有未验收状态
OMITTED_ISSUES = 原始 active issue_id 集合 - 当前账本 issue_id 集合
DUPLICATED_ISSUES = 在账本或任务中重复归属的原始 issue_id
```

`REMOTE_VERIFIED` 的匹配依赖规则语义、稳定符号／上下文及重命名／迁移关系，不能仅凭旧服务端 defectId 不存在或旧行号不报错就判定已修复。

最终成功必须同时满足：

1. 原始输入和任务守恒检查通过，`OMITTED_ISSUES=0`、`DUPLICATED_ISSUES=0`。
2. 非文件头问题没有 `UNASSESSED`、`PRESENT`、`PATCH_PROPOSED`、`LOCAL_CLEAR`、`LOCAL_VERIFIED`、`UNKNOWN`、`BLOCKED`、`STALE` 或待审批例外。
3. 同版本服务端全量复扫成功，分页完整、规则与范围不缩减；未验收的新问题也为零。
4. 所需本机回归、真机功能／认证及提交链路验证通过；未运行就明确写 `NOT_RUN`，不能假设通过。
5. 远程门禁实际通过。若使用例外，需远程认可且单独披露，不得与代码修复混算。

任何一项不满足，最终验收返回非零；中间库存完整性检查通过不代表上述闸门通过。

`scripts/codecheck_controller.py` 已继续实现以下模块：

- 原始服务端记录与全部 10624 条本地记录对照。匹配原路径、规则、原行号和原消息的完整多重集合；行号仅用于关联原始扫描，不用于判断当前缺陷消除。服务端 `defectId` 并不全局唯一，不按该字段去重；同键多条保留所有候选及原始序号，不猜测一一对应。
- 受控 Ruff 运行器。使用绝对工具路径，绑定可执行文件摘要和版本，固定规则、隔离配置、忽略 `noqa` 屏蔽，保存命令、工作目录、输出、退出码和超时。JSON 模式、诊断范围、位置、规则与退出码必须一致；警告、执行异常、非法输出不得当作零问题。
- 逐条本地判定。当前适配空格、多语句、嵌套定义空行、参数 snake_case，以及全部物理行不超过 120 字符的充分条件；另以 AST 检查 assert、lambda 赋值及 `print`／`__import__` 符号。Ruff 结果按当前整文件同规则保守关联，避免用移动后的旧行号漏掉问题。仍有长行时保留 `UNKNOWN`，不猜测远程对字符串、URL 等内容的例外。其它规则一律保留 `UNKNOWN`，不批准例外。
- 带进程锁、原子文件写入和前向哈希链的事件账本。每次核验生成独立事件，原事件不改写；读取时检查连续序号和链条，不接受删除中间事件或损坏记录。最后一个链头须由用户／CI 外部保管；没有外部锚点时不能声称能识别整个尾段被删除或整条链被重写。
- 证据失效与逐文件队列。绑定完整 Git 跟踪文件及未忽略的新文件、文件模式、当前验证器代码和 Ruff 二进制；变化后显示 `STALE`。目录、缺失路径、未知规则仍列入全部 5954 条义务。依赖环境中的未跟踪／已忽略文件、已安装包和系统工具链不在此仓库摘要内，不能据此宣称环境级可复现认证。
- 回归运行器。固定使用显式解释器和 `tests/` 文件，指向待修仓库的 `src`，保存 pytest 原始结果与源码摘要；仅记录 `RUNNER_PASS`，不自动把跳过测试、退出码零或格式检查通过提升为问题认证。
- `gate` 非零退出闸门。当前尚不导入服务端复扫，因此始终拒绝“整改完成”；即使本地全部检查通过，也不能绕过远程认证。

运行时账本必须与冻结盘点目录、被评估仓库分开，避免自身输出污染摘要。以下命令在本地工作树执行；`PY`、`REPO` 和 `RUFF` 指向实际可用环境：

`report` 输出全量问题状态和按路径排序的队列；中间报告命令退出码零只表示成功生成报告。`gate` 当前预期退出码为 1，不是运行器故障。`assess` 运行器故障返回非零，并将不能判断的问题保留为 `UNKNOWN`。原始接口对照使用 `crosswalk --state ... --raw ... --out ...`，不覆盖已有输出。

## 七、本轮实际应用边界

当前沙箱能读取、不能写入用户的质量整改仓库，因此采用相同 HEAD 的可写副本实施修复，最终生成带前后摘要、上下文校验和备份回滚能力的交付包。没有自动修改用户原仓库、提交或推送。

Harness 工具与控制器自测保留在当前工作树，不把额外工具文件加入质量整改仓库的扫描范围。首批 13 个既有待修文件的修复在回归中触发了冻结资产保护，因此补充必要的历史验证器、自测与显式资产修订。交付包另在独立副本执行应用、重复应用和回归验证，防止仅在开发副本通过。

首次本地核验发现四个文件仍有 17 处 Ruff 空格诊断，按整文件同规则关联到 79 条原始记录；79 不是独立代码位置数。该格式修复阶段仅插入空格，改动前后 AST 相同，原七行 license 头逐字不变：

- `scripts/templates/coverage_kernels.py`。
- `scripts/templates/implementation_witness_kernels.py`。
- `src/triton_eval/compilation_evidence.py`。
- `tests/test_backend_capture.py`。

继续补充 AST 适配后，将正常代码中的 9 个 lambda 赋值改成具名函数、8 处 `__import__` 改成显式导入。保留捕获回调的闭包、异常传播、参考实现投毒检测和测试意图，不改公共算子签名。另将诊断脚本的时间改成显式 UTC 取时再转换本地时区，保持原本的本地时间目录格式。累计修改 13 个既有文件，不改任何已有文件头。

完整回归确实发现这次源码变化使 14 份 `evaluation-assets.json` 不再与当前资产匹配，产生失败；该失败已作为原始证据保留，不能用格式改动为由忽略。解决方式不是关闭校验或原地抹掉旧身份，而是沿用已有迁移机制，显式发布 `codecheck-harness-20261104` 修订：

- 原始 `origin_assets_hash` 不变，上一修订的索引按原内容归档，原迁移元数据完整保存在新迁移记录中。
- 每份新索引绑定当前源码、新迁移记录及前一修订归档。历史验证器校验归档自身摘要、相同用例 manifest 和原迁移元数据摘要；伪造、丢失、重复历史记录仍拒绝。
